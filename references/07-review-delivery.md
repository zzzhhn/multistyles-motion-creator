# 07 · 审片、导出、平台版、清理

## 节奏

1. 原型阶段：导出 30 秒左右的原型 MP4，加一张接触表，交用户看方向。
2. 铺开后：全部单元做完就导一版粗剪，未完成的单元显示为占位格也先交。用户 eyeball 成片比任何审片代理都有效。
3. 用户给意见后：写进单元标准，续用原队伍改；配乐单独迭代，用换音轨出新版。
4. 定稿前：最多一个代理粗看一遍硬伤。

## 审片（要轻）

- 用户明确要求：新版出来后**不要再派一堆审片代理，最多一个大体过一下**。这次 v09 派了三个审片人（每人 24 格，逐格七项打分），用时 70 到 85 分钟，其中一个因读图太多撞上下文上限中途失败；用户认为效率太低。
- 轻量审片用 `templates/REVIEW_BRIEF-light.md`：每 4 秒抽一帧拼成接触表，抽 12 条缝看原尺寸，全片逐帧灰度扫描找黑帧和跳变，最多列 10 条「观众不用提示就会觉得哪里坏了」的硬伤；不评审美，不评音乐。实际用时约 35 分钟，找到 1 条。
- 如果确实需要逐格审（例如第一次大规模铺开后），每个审片代理看的图控制在约 80 张以内，结论按单元拆给原队伍。审片人在 v09 发现的共性问题已写进 04：记忆点太晚、主事件太小、队伍穿过道具。

## 导出

- 主片：`node tools/build.cjs xiyou.html film.html && node tools/export.cjs xiyou.html out/成片.mp4`。页面内 WebCodecs 编码，2560×1440@60 用 `avc1.640033`、32 Mbps；7 分 47 秒约 225 到 260 秒导完，约 1.8 GB。17 项检查包括：faststart、双轨、帧数、统一时间戳、关键帧间隔、AAC 48 kHz 立体声、时长、`<video>` 实际尺寸、音频解码非静音、`VideoDecoder` 全片解码、macOS `mdls`/`afinfo`。
- 只导一部分：`EXPORT_Q='cells=1,2,3' node tools/export.cjs ...`。
- 导出前检查：全部源文件 `node --check`；导出后 `ffmpeg -af ebur128=peak=true` 测响度（目标 −14 LUFS，真峰 ≤ −1 dBTP），并从 MP4 里解码抽一段接触表看画面（不要只看导出工具自己的检查）。

## 平台版（9:16、1:1）

不要把横版硬裁成竖版。示例的做法：`src/platform.js` 让 film 画到离屏画布（`window.__FILM_CANVAS = 'film'`），再重新排版：

- 上方：当前单元的大字标题（第 N 难加名目加画风年代），换单元时上滑切换；开场和片尾显示片名卡。
- 中间：裁过的画廊画面。裁切框在队伍处于格内时跟着当前画框走（保证框内字完整），快过缝时滑回跟着队伍。
- 下方：9:16 是随旅程点亮的全部单元小网格；1:1 是一排进度方块。开场和片尾的总览阶段隐藏画廊裁切，避免和页面自己的标题、网格重复。
- 生成：`node tools/mkplatform.cjs`（从 film.html 派生，保证脚本一致）；导出：`EXPORT_Q='profile=9x16' EXPECT_W=1440 EXPECT_H=2560 node tools/export.cjs src/platform.html out/竖版.mp4`，1:1 用 `profile=1x1`、`EXPECT_H=1440`。
- 检查竖版时用原比例的帧看，不要把竖帧拼进横版布局（这次因此误判过一次「标题撞顶」）。

## 转发用压缩版

`ffmpeg -i 成片.mp4 -c:v libx264 -preset veryfast -crf 22 -pix_fmt yuv420p -c:a copy -movflags +faststart 成片-share.mp4`：主版约 1.8 GB 压到约 580 MB，竖版和方版约 300 MB。平时看分辨不出差别；剪辑、二次转码用原版。

## 清理

定稿后用户会要求删旧版。删之前确认源码和工具不依赖要删的文件（`grep` 一遍），删完从源码再渲染一帧确认工程还能跑。

- 可删：旧版成片和压缩版、中间版画面母版、原型 MP4、旧的单文件构建、旧版音频母带和试听、审片和制作截图、各队的检查拼图、早期副本目录。
- 保留：定稿的各版本和压缩版、全部源码与工具、制作标准、各队日志、审片文字报告、定稿配乐母带、总表和参考资料。
- 不动别人的文件夹（例如用户下载目录里别的 agent 扒的参考片），只告诉用户有多大、可以删。
- 这次清理释放约 10 GB，项目从 16 GB 降到 5.8 GB；剩下的基本是三个版本的成片。

## 第二部片子补充（《二十四节气》）

- **全片帧差扫描**：`python -I scripts/scan.py out/<片>.mp4 --t0 <第一个单元开始> --unit <单元秒数> --n <单元数>`，把相邻帧差按「过渡末尾、过渡内、其余」分组列最大值。过渡末尾那一组明显高于过渡内，就是收尾一跳（v2 修前 15.5，修后 4.6）；其余组里最大的几处要么是设计好的闪光，要么是 bug，逐个看前后帧。这一步不用浏览器，一分钟。
- **粗看代理照旧只派一个**，简报写清「什么是设计」（过渡遮罩、题签、片头片尾）：v2 它找出 5 处真问题（过渡收尾一跳、题签压住画风自带的字、窄容器里的字超出、卧起一帧跳变），修完再扫一遍确认。v1 它报 0 条，但用户提了四条结构问题：粗看抓不到结构层，结构层要按 `11-error-analysis.md` 第六节自查。
- **平台页和主片页同一份脚本列表**：第一次竖版和方版漏了乐器脚本、没有音轨（导出检查报了 5 项失败才发现）。导出后四个版本都要测一遍响度，确认有音轨。
- **四个版本**：主版、循环版（去片头片尾、尾接首；配乐也做成首尾相接的版本，尾音绕回开头）、竖版、方版，各出一个转发压缩版。
- **旧版先挪到 `out/v1/`**，等用户认可新版再删。

## 发成公开仓库前的脱敏（用户要求记住的规则）

用户：「确实应该脱敏，解决这些本地化问题」。发布 skill 或示例工程前逐项查：

1. 公司名、内网域名、镜像源、内部工具名、凭据形状的字符串（token、key、cookie）。
2. 本机绝对路径（`/Users/<名字>/…`、`~/.<agent>/…`）：改成相对路径、「本目录」，或环境变量（音频工具用 `$AUDIO_TOOLS`）。
3. 本机 agent 名和只在本机有的 skill：改成「用户的另一个 agent」「本机有就用」。
4. 写死的工具路径（Playwright）：改成按顺序查找的解析器（`scripts/pw.cjs`），改完实际跑一次。
5. 打包进来的第三方库和参考过的项目：带许可证原文，写进 `THIRD_PARTY_NOTICES.md`。
6. 不进仓库：成片视频、渲染出来的音频、采样库本身（多数采样授权禁止再分发）、每台机器各自生成的缓存（例如带绝对路径的 `tuning.json`）。
